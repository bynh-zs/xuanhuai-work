# 一、系统架构：一个应用、两个入口、一套数据

## 1. 整体链路

```
                ┌──────────────── 飞书自建应用（宣怀bot）────────────────┐
   私聊/群聊  → │ 事件订阅 → entrypoints/feishu/normalize.py 路由          │
                │     ├─ assistant（知识库/对话）                          │
                │     ├─ volunteer（志愿登记、查询、审核）                 │
                │     └─ reimbursement（报销提交、查询）                   │
                │        ↓                                                │
                │  各模块 service 层（校验 / 状态机 / 时长计算）           │
                │        ↓                                                │
                │   同一数据库 + 同一业务作用域                            │
                └─────────────────────────────────────────────────────────┘
                                    ↑ 复用 service 层
   飞书内 H5  → JSAPI 取授权码 → 后端换 open_id → 映射 member_id → 同上
```

机器人入口和网页入口不是两套系统：网页只负责"取身份 + 调接口 + 展示"，业务规则全部落回原有 Python service 层，数据库也只有一份。

## 2. 身份链路

1. 网页在飞书客户端内调用 `h5sdk.requestAuthCode` 拿到授权码；
2. 授权码交后端，后端换取 `open_id`（服务端校验，前端不参与身份判定）；
3. `platform/identity/feishu.py` 把 `open_id` 映射成机器人使用的同一内部成员编号 `member_id`；
4. 之后所有接口以 `member_id` 为准，用户不能自己填编号决定身份。

本地开发阶段这条链路留了桩：前端在 `127.0.0.1` 下返回固定测试身份，后端身份依赖也返回固定测试用户，接口形状按正式实现预留，部署后替换实现即可（见 `code/feishuAuth.ts`）。

## 3. 作用域为什么不能因入口而变

现有业务作用域 = 应用标识 + 租户 + 运行模式三者派生的键。志愿模块在这个键上加锁做并发控制，记录也按这个键归档。

风险点：如果网页端为了"独立"另起一个作用域（比如把入口名 `web` 塞进去），网页就会查到另一套空数据，出现"机器人有记录、网页没记录"的假故障。所以网页入口必须沿用机器人派生出的同一个作用域，这一点在实现时是硬约束。

## 4. 五条一致性约束（来自任务书，也是设计依据）

| 约束 | 落实方式 |
|------|----------|
| 身份一致 | 服务端换 open_id → 映射 member_id；前端不传、不选身份 |
| 数据一致 | 共用同一数据库与同一业务作用域；网页与机器人读写同一张记录表 |
| 权限一致 | 复用机器人端审核人/负责人/导出人名单；前端隐藏按钮之外，后端必须再校验一次 |
| 执行一致 | 共用 service 层的校验、确认、防重复与并发控制；重复点击与并发审核都走同一状态机 |
| 入口共存 | 在现有自建应用里加志愿入口，保留报销入口；路径、回调、代理由公共维护者统一核对 |

## 5. 当前实现与任务书建议路径的差异

任务书建议正式网页放 `services/volunteer-web/`。实际做法是复用主项目已有的 `web/` 前端原型（`web/src/features/volunteer/VolunteerPanel.tsx`），把它从"本地测试页"改造为六个功能页的正式页面。

理由：原型已具备完整交互，另起一套工程会形成两份前端代码；且报销网页已在同仓库 `services/reimbursement/` 有独立部署物，志愿侧规模更小，先复用主前端可减少公共维护者的部署核对成本。

该差异已在部署说明中写明，供评审确认是否需要迁移到独立目录。
